# Аудит Meta: FP → BM → РК, Retry и Sync

Область: приватный браузерный транспорт, создание Fan Page, создание Business Manager,
привязка страницы, создание рекламного аккаунта, восстановление задач, сохранение
подтверждённых объектов и отображение результатов в Workspace.

## Подтверждённые дефекты и исправления

| Узел | Дефект | Последствие | Исправление |
|---|---|---|---|
| FP inventory | Чтение DOM после `commit`, короткое ожидание, повторная навигация при пустом документе | FP отсутствуют в текущем чтении, хотя сохранённые страницы есть | Ожидание `domcontentloaded` в пределах прежнего таймаута, settle 900 ms, до семи чтений одного документа с интервалом 500 ms; Relay-ответы сохраняются |
| FP inventory | Сканировались только первые 900 ссылок | Ссылки страниц дальше в документе пропускались | Восстановлен предел 2500 ссылок |
| Sync | `sync_partial` зависел от наличия сохранённых страниц, а не от live-проверки | Сообщение полного успеха при незавершённой проверке FP | Частичный результат определяется `pages_live_verified`; предупреждение прямо сообщает о сохранённом состоянии |
| BM CREATE | Приватный CREATE отправлялся до сохранения `CREATE_SUBMITTED` | При остановке воркера новый Job мог отправить CREATE повторно | Существующий native `before_submit` связан с durable checkpoint через все слои вызова |
| BM CREATE | Полученный ID сохранялся только после попытки привязки FP | Остановка во время привязки могла потерять подтверждённый ID BM | Точный ID и response path сохраняются до привязки страницы |
| BM cross-Job resume | Учитывались только неопределённые CREATE с непустым `business_ids_before` | Пустой или отсутствующий baseline позволял новому Job начать CREATE | Неопределённое состояние переносится независимо от размера baseline; отсутствие baseline блокирует повтор |
| BM reconciliation | Пустой baseline считался отсутствующим | Первый BM профиля нельзя было восстановить через список новых объектов | Пустой список принимается как валидный baseline; отсутствие списка обрабатывается отдельно |
| BM transport | Не использовался явный признак фактической отправки | Сбой до отправки мог превращаться в неопределённый результат | `request_may_have_been_sent=False` даёт retryable ошибку до отправки; `True` без результата требует reconciliation |
| BM rejection/resume | После отказа Meta в имени оставалась фаза отправленного CREATE; resume не всегда отражался в результате | Новый Job мог блокироваться из-за уже отклонённого запроса; неверный признак resumed | Отказ в имени сохраняется как `CREATE_REJECTED`; восстановление существующего ID отмечается как resumed |
| BM recovery | При потере ответа и в legacy-вызове без FP оставались чтения официального Graph API | Приватный процесс зависел от токена и официальных разрешений | Эти обращения удалены; recovery использует браузер и checkpoints |
| РК recovery | Проверка существующих РК читала официальный Graph; его пустые ответы сокращали browser proof | Не соответствовало выбранному приватному процессу; токен мог влиять на решение о новом CREATE | Официальный inventory отключён; восстановленные Graph diagnostics не сокращают независимую проверку браузером |
| РК capture | `created_during_capture` сразу приводил к сохранению успеха | ID мог быть объявлен созданным без подтверждения в выбранном BM | До успеха выполняется проверка точного ID в этом BM; при неуспехе сохраняется неопределённый результат |
| FP batches | Между Job учитывались только полностью успешные пакеты | Успешно созданные FP внутри упавшего пакета могли создаваться повторно | Чтение worker state включает подтверждённые `created_pages` из незавершённых пакетов и сохраняет BM/РК-привязку |
| FP cross-Job recovery | Новое задание не проверяло неопределённый CREATE предыдущего задания | Повтор CREATE той же страницы | Добавлен поиск неопределённого CREATE по профилю и имени до нового CREATE |
| FP absence proof | Три parseable/пустых списка считались доказательством отсутствия | Поздняя загрузка/распространение страницы могло привести к дублю | Список без признака полноты не разрешает повтор CREATE; положительное обнаружение страницы позволяет восстановление |
| Worker queue | Проверка `QUEUED` выполнялась до ожидания profile lock | Два consumer могли последовательно исполнить один item | Статус повторно читается внутри блокировки до исполнения |
| Snapshot restore | Импорт не восстанавливал `retryable` у items/tasks | Retry исчезал после восстановления БД из mirror | Поле импортируется и обновляется для обеих таблиц |
| Job idempotency | Поиск ключа и вставка выполнялись без общего write transaction | Одновременные запросы с одним ключом могли конфликтовать | `BEGIN IMMEDIATE` охватывает поиск и создание Job |

## Проверка кода

Общий прогон: `python -m unittest discover -s tests` — **449 проверок, OK**.
В существующем наборе есть проверки исходного кода и контрактов; это число нельзя
трактовать как 449 реальных операций в Meta.

Добавлены 15 поведенческих регрессионных проверок в
`python_backend/tests/test_system_audit_regressions.py`:

1. Остановка после приватной отправки BM блокирует повтор CREATE в новом Job.
2. Остановка во время Page attach сохраняет BM ID; Retry пропускает CREATE.
3. Пустой baseline BM восстанавливается между Job.
4. Явное состояние отправки определяет transport error; официальный API не вызывается.
5. Recovery РК не читает официальный токен.
6. Gate перед отправкой проходит до native transport.
7. Неподтверждённый capture ID РК не сохраняется как успех.
8. Подтверждённый capture ID РК сохраняется в выбранном BM.
9. Старые Graph diagnostics не уменьшают число browser checks.
10. `retryable` переживает импорт snapshot, и Retry ставит задачу обратно в очередь.
11. Два consumer одного queued item исполняют resolver один раз.
12. Восемь одновременных запросов с одним idempotency key получают один Job.
13. Подтверждённая FP из частичного пакета доступна следующим Job вместе с BM-привязкой.
14. Новый Job не повторяет неопределённый CREATE FP предыдущего Job.
15. Поздняя загрузка FP обнаруживается без второй навигации.

Два исходных тестовых модуля были несовместимы с текущими production-интерфейсами:
один импортировал удалённые функции, другой подменял старые методы контроллера.
Они переведены на текущие интерфейсы. Тест восстановления привязки по-прежнему
требует одного CREATE, ошибки привязки и успешного Retry без второго CREATE.

## Что подтверждалось production-логами до исправлений

В текущем исходном deployment профиль 7 подтверждал существующий BM
`61594753560938` и РК `2172569806673120`. Один запуск подтверждал четыре FP
после второго чтения, другой возвращал пустой браузерный документ/Relay inventory
и сохранял старые FP для отображения. Это подтверждает нестабильность текущего
чтения FP; наличие старых FP само по себе не доказывает live-проверку.

Полный возврат к сборке от 27 сентября не выполнен: в ней Sync использовал
официальный Graph API, что противоречит выбранному сейчас приватному процессу.
Из прежнего поведения восстановлены ожидание документа и предел DOM-сканирования.

## Практические пределы

- Регрессии проверяются с подменёнными Meta/browser ответами и настоящей SQLite.
- Реальное создание новых FP/BM/РК в этом прогоне не выполнялось. Полный сценарий
  создания нельзя объявить подтверждённым только по тестам или чтению существующих объектов.
- Неопределённый CREATE без точного ID и без достоверного baseline остаётся
  заблокированным до подтверждения. Это защищает от повторного создания, но не
  решает автоматически все старые повреждённые checkpoints.
- Полнота FP inventory, авторизация профиля, ограничения Meta и актуальность
  приватных persisted mutations должны подтверждаться конкретным live-запуском.
- Funding, рекламные кампании, объявления, биллинг и все остальные экраны не
  проходили полный live-сценарий в рамках этого исправления.
