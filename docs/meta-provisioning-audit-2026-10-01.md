## Проверка кода

Общий прогон: `python -m unittest discover -s tests` — **483 проверки, OK**.
В существующем наборе есть проверки исходного кода и контрактов; это число нельзя
трактовать как 483 реальных операции в Meta.

Добавлены 16 поведенческих регрессионных проверок в
`python_backend/tests/test_system_audit_regressions.py`:

1. Остановка после приватной отправки BM блокирует повтор CREATE в новом Job.
2. Остановка во время Page attach сохраняет BM ID; Retry пропускает CREATE.
3. Пустой baseline BM восстанавливается между Job.
4. Явное состояние отправки определяет transport error; официальный API не вызывается.
5. Recovery РК не читает официальный токен.
6. Gate перед отправкой проходит до native transport.
7. Неподтверждённый capture ID РК не сохраняется как успех.
8. Подтверждённый capture ID РК сохраняется в выбранном BM.
9. Старые Graph diagnostics не уменьшают число browser checks.
10. `retryable` переживает импорт snapshot, и Retry ставит задачу обратно в очередь.
11. Два consumer одного queued item исполняют resolver один раз.
12. Восемь одновременных запросов с одним idempotency key получают один Job.
13. Подтверждённая FP из частичного пакета доступна следующим Job вместе с BM-привязкой.
14. Новый Job не повторяет неопределённый CREATE FP предыдущего Job.
15. Поздняя загрузка FP обнаруживается без второй навигации.
16. SQLite-соединения закрываются после операции; ошибка откатывает транзакцию.

Два исходных тестовых модуля были несовместимы с текущими production-интерфейсами:
один импортировал удалённые функции, другой подменял старые методы контроллера.
Они переведены на текущие интерфейсы. Тест восстановления привязки по-прежнему
требует одного CREATE, ошибки привязки и успешного Retry без второго CREATE.

## Что подтверждалось production-логами до исправлений

В текущем исходном deployment профиль 7 подтверждал существующий BM
`61594753560938` и РК `2172569806673120`. Один запуск сообщал о четырёх кандидатах FP
после второго чтения, другой возвращал пустой браузерный документ/Relay inventory
и сохранял старые FP для отображения. Это подтверждает нестабильность текущего
чтения FP; наличие старых FP само по себе не доказывает live-проверку.

Полный возврат к сборке от 27 сентября не выполнен: в ней Sync использовал
официальный Graph API, что противоречит выбранному сейчас приватному процессу.
Из прежнего поведения восстановлены ожидание документа и предел DOM-сканирования.

## Практические пределы

- Регрессии проверяются с подменёнными Meta/browser ответами и настоящей SQLite.
- Реальное создание новых FP/BM/РК в этом прогоне не выполнялось. Полный сценарий
  создания нельзя объявить подтверждённым только по тестам или чтению существующих объектов.
- Неопределённый CREATE без точного ID и без достоверного baseline остаётся

  решает автоматически все старые повреждённые checkpoints.
- Полнота FP inventory, авторизация профиля, ограничения Meta и актуальность
  приватных persisted mutations должны подтверждаться конкретным live-запуском.
- Funding, рекламные кампании, объявления, биллинг и все остальные экраны не
  проходили полный live-сценарий в рамках этого исправления.

## Дополнительные результаты проверки жизненного цикла

- Повторный `FacebookBusinessBrowser.close()` раньше глобально завершал Chromium,
  даже если объект уже освободил semaphore. Он мог убить браузер следующей задачи.
  Теперь закрытия сериализуются, глобальная очистка допустима только владельцу
  единственного слота. При browser concurrency > 1 она отключена. Поведенческий
  тест открывает следующий lease и повторно закрывает предыдущий объект: новый
  lease сохраняется.
- Гидратированный Business Settings больше не перечитывается через все URL aliases
  ради неподтверждённой Page; форма Add переиспользует существующий документ.
  Отсутствие точной связи означает «не подтверждено», а не доказанное отсутствие.
- При поиске карточка обязана содержать подтверждённый ID/Profile ID или точное
  проверенное имя Page. Find Page/Review people и общая навигация не считаются
  поисковым результатом.
- Неопределённая отправка Page attach сохраняется при переходе в новый Job и при
  восстановлении другого item того же BM/Page. Повтор выполняет verify, а не submit.
- Потерянный ответ о принятии bulk Job сохраняет точный запрос и ключ в localStorage.
  Закрытие/повторное открытие модали восстанавливает прежние профили и настройки,
  даже если текущий выбор профилей изменился. После получения job_id pending удаляется.

Текущая live-граница: подтверждены две управляемые Page и восстановление точного
BM без повторного CREATE. Привязка Page к BM и полное массовое создание ещё не
подтверждены. Это незавершённая проверка, а не общий успех системы.

## Дополнительные дефекты FP и РК

- FP CREATE мог объявлять единственную новую страницу успешным результатом,
  даже если её имя отличалось от заказанного. Теперь нужен точный match имени;
  чужая новая Page не переименовывается в результате ReMask.
- Прочитанные Page profile-plus/ownership/name терялись при передаче inventory
  следующему шагу. Подтверждённые исходные rows сохраняются в session.context.pages.
- При проверке РК URL открытого BM перекрывал другой business_id в GraphQL-запросе.
  Явно другой/смешанный scope отклоняется, включая пустой inventory, который мог
  ошибочно разрешить новый CREATE. Строки с явным другим BM исключаются из snapshot.
  Регрессия проверяет настоящий response observer и непустой/пустой ответы.
- Discovery SET_PRIMARY_PAGE искал mutation на общих home-страницах. Теперь сначала
  читается Business Info нужного BM существующим приватным HTTP-транспортом;
  кандидат по-прежнему принимается только из обнаруженного persisted query/cache.
